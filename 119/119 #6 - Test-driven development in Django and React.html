Test-driven development: red, green, refactor

Write a failing test, make it pass, clean up. TDD turns “it should work” into “here’s proof.”

SDGKU FSDITopic 119.6
Why this matters

Tests written last only confirm what you built

The risk

Tests are written last (or never), so they only confirm what exists.

What usually happens

Refactors and AI edits silently break features.

The result

Bugs appear at demo time, not development time.

A failing test first forces you to define “done” before you code.

A framework you can reuse

The TDD cycle

1

Red

Write a failing test that defines the behavior.

2

Green

Write the minimum code to pass.

3

Refactor

Clean up with tests as a safety net.

4

Small steps

One behavior per cycle.

5

Run often

Every save, every commit.

TDD in Django

Django: TestCase → fail → implement

  • Write the test in tests.py (TestCase or pytest-django).
  • Run python manage.py test — watch it fail.
  • Implement the model / view logic.
  • Re-run until green, then refactor.
class ProductTests(TestCase):
    def test_out_of_stock_hidden(self):
        Product.objects.create(
            name="Mug", stock=0)
        res = self.client.get("/products/")
        self.assertNotContains(res, "Mug")

TDD in React

React: Testing Library → fail → implement

  • Write the test with Vitest/Jest + React Testing Library.
  • Run npm test — watch it fail.
  • Build the component behavior.
  • Green, then refactor.
test("hides out-of-stock products", () => {
  render(<ProductList
    items={[{name: "Mug", stock: 0}]} />);
  expect(screen.queryByText("Mug"))
    .toBeNull();
});
SDGKU FSDITopic 119.6
Using AI as a design partner, not autopilot

AI and TDD are a natural pair

Good use

  • Ask AI for the failing test first, then implement yourself
  • Ask for edge-case tests per behavior
  • Don’t let AI write the code and its own passing tests uncritically
!

Guardrail

If you can’t write the test, you don’t know the requirement yet.
